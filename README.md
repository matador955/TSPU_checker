# Мини-проект "TSPU_checker"

PowerShell-скрипт для проверки того, насколько сильно подсети хостинга заблокированы ТСПУ для доступа из России. Помогает решить две задачи: оценить, стоит ли менять IP у текущего провайдера, и заранее прикинуть, годится ли новый провайдер под новый VPS.

---

## 1. Зачем этот скрипт

С сентября 2026 ТСПУ (технические средства противодействия угрозам) начали блокировать доступ не к отдельным IP-адресам, а к целым диапазонам. Под такую блокировку массово попадают подсети хостинг-провайдеров, и это превращает задачу "найти место для размещения своего VPS" в сложный квест.

Типичная картина, которую видит владелец сервера, расположенного за границей:

- сайт (порты 80/443) и даже SSH на нестандартном порту **не открываются из России**;
- из Европы тот же сервер работает штатно;
- при этом `ping` и `tracert` до сервера из России **проходят**.

Это характерный признак блокировки на уровне TCP (L4): ICMP-пакеты пропускаются, а TCP-соединения (SYN) отбрасываются на трансграничном переходе. Домен, регистратор и содержимое сайта роли не играют, т.к. режется сам сетевой доступ к IP.

### В каких ситуациях поможет скрипт

**Сценарий А. У вас уже есть заблокированный сервер.** Нужно понять масштаб проблемы: заблокирован только ваш адрес или вся подсеть провайдера, и есть ли у провайдера в этой локации хоть один условно "чистый"" диапазон. Многие провайдеры предлагают услугу «смена IP» — но платить за неё имеет смысл, только если есть незаблокированные подсети. Если задеты все, то смена IP внутри провайдера не поможет.

**Сценарий Б. Вы выбираете нового провайдера под новый VPS.** Ещё до покупки полезно оценить, насколько его адресные диапазоны попали под блокировки из РФ.

### Общая логика диагностики

Раз ТСПУ оперируют целыми диапазонами, то проверка строится вокруг *автономной системы провайдера* (**ASN**) — это идентификатор всей сети провайдера, внутри которой лежат его адресные диапазоны (префиксы):

1. Определить ASN провайдера (в сценарии А — от своего заблокированного IP, в сценарии Б — по названию провайдера или по его собственному IP).
2. Получить список подсетей, которые этот ASN анонсирует.
3. Точечно проверить несколько подсетей из этого списка дважды, из России и из Европы, и сравнить.

### Что делает скрипт

Берёт случайную выборку адресов внутри одной подсети `/24` и по каждому проверяет:

- **пинг** (ICMP);
- **SSH** — последовательно порты 22, 222, 2222 (до первого ответившего).

SSH проверяется всегда, независимо от пинга. Прогон нужно запускать дважды с одним и тем же набором адресов: один раз из России (напрямую) и один раз из Европы (через включенный временный VPN), после чего скрипт сводит результаты и показывает, какая доля живых серверов теряет TCP-доступность именно из России.

## 2. Что нужно для работы

- **Windows 10 или новее** со встроенным Windows PowerShell 5.1 (ничего доставлять не нужно, внешних зависимостей нет).
- **Временный VPN с выходом из России** (чаще всего это Европа). Он нужен для эталонного прогона, чтобы увидеть, как та же подсеть выглядит «снаружи», из точки без блокировок. Подойдёт любой рабочий VPN, который на время прогона пропускает **весь** трафик машины через европейский узел.

> На точность влияет «чистота» выходного IP вашего VPN. Если сам VPN-узел окажется заблокированным на целевой подсети, эталон получится некорректным (см. раздел «Интерпретация», пункт про блокировку за спам).
> 
> Расход трафика при проверке минимальный (килобайты), поэтому подойдет практически любой доступный/беспланый VPN, например adguard.

## 3. Как использовать скрипт

### Шаг 1. Определить ASN и подсеть

Всё делается через сайт [bgp.he.net](https://bgp.he.net/).

**Сценарий А — от своего заблокированного IP:**

1. Откройте [https://bgp.he.net/](https://bgp.he.net/) и введите в поиск свой IP (в примере ниже — `45.131.185.118`).
2. На странице IP будет указан анонсирующий его **ASN**. Перейдите на него.
3. Откройте вкладку **Prefixes v4** — это полный список IPv4-подсетей провайдера.

**Сценарий Б — по названию провайдера:**

1. Найдите провайдера на [https://bgp.he.net/](https://bgp.he.net/). Варианты:
   1. Введите название провайдера прямо в поиск
   2. Поищите на форумах или в телеграм-группах упоминания о провайдере, и найдите любой упомянутый IP, выданный им для чьей-то VPS  
2. В результатах найдите **ASN** и перейдите на него.
3. Так же откройте вкладку **Prefixes v4**.

**Выбор подсети для проверки.** Скрипт работает с блоком `/24` (255 адресов), поэтому в качестве `SubnetBase` берутся **первые три октета**:

- префикс `45.131.185.0/24` → `SubnetBase = 45.131.185`;
- если префикс крупнее `/24`, то он содержит в себе несколько блоков `/24`, которые проверяются по отдельности. Например, `/23`-блок `45.131.184.0/23` — это две подсети: `45.131.184` и `45.131.185`.

Чтобы оценить провайдера в целом, прогоните несколько его подсетей по одной за раз.

> **Пример из практики.** Хостер JustHost.Asia, [AS26383](https://bgp.he.net/AS26383), — на момент написания скрипта у его диапазонов фиксировались массовые проблемы с доступностью из РФ. Ниже все команды приведены на его подсети `45.131.185`.

### Шаг 2. Подготовить запуск

Положите `TSPU_checker.ps1` в отдельную папку (например, `D:\JustHost`). Рядом со скриптом будут создаваться файлы отчётов. Откройте PowerShell в этой папке.

> **Совет: одна папка на провайдера.** Все результаты копятся в папке со скриптом, а сводный режим (см. Шаг 4) сводит статистику по всем файлам в ней. Поэтому под каждого провайдера удобно завести отдельную папку, положив туда копию скрипта, и тестировать в ней его подсети одну за другой. Тогда в конце получается общая картина именно по данному провайдеру, не смешанная с другими проверками.

При первом запуске из PowerShell бывает так, что система запрещает выполнение скриптов. Тогда разрешите запуск для текущего окна командой:

```powershell
Set-ExecutionPolicy -ExecutionPolicy Bypass -Scope Process
```

Запускать скрипт нужно с префиксом `.\`:

```powershell
.\TSPU_checker.ps1 ...
```

### Шаг 3. Два прогона + сравнение

Скрипт различает прогоны параметром `-Network`: `RUS` — проверяемая сеть (из России), `EUR` — эталонная сеть (например из Европы). Порядок:

```powershell
# 1. Прогон из России — БЕЗ VPN
.\TSPU_checker.ps1 -Mode Scan -Network RUS -SubnetBase 45.131.185

# 2. Включите VPN с выходом в Европу, затем эталонный прогон
.\TSPU_checker.ps1 -Mode Scan -Network EUR -SubnetBase 45.131.185

# 3. VPN можно выключить. Сведение результатов
.\TSPU_checker.ps1 -Mode Compare -SubnetBase 45.131.185
```

Первый прогон формирует случайную выборку адресов и сохраняет её в файл `targets_<подсеть>.txt`. Все последующие прогоны той же подсети (в том числе второй прогон при включенном VPN) берут адреса **из этого файла**. Так обе проверки идут строго по одному набору. 

> **Совет:** если захотите изменить список тестируемых IP, то либо удалите файл `targets_<подсеть>.txt` (тогда скрипт пересоздаст список с новыми случайными адресами), либо отредактируйте файл вручную (структура простейшая, одна строка = один IP).

Порядок запуска RUS/EUR некритичен, важно лишь, чтобы оба прогона отработали до запуска `Compare`.

### Файлы, которые создаёт скрипт

Все файлы сохраняются в текущей папке со скриптом:

| Файл                                                      | Что это                                                                  |
| --------------------------------------------------------- | ------------------------------------------------------------------------ |
| `targets_<подсеть>.txt`                                   | список проверяемых адресов (общий для обоих прогонов)                    |
| `result_<подсеть>_RUS.json` / `result_<подсеть>_EUR.json` | машиночитаемые результаты прогонов (нужны для автоматического сравнения) |
| `<подсеть>_RUS.txt` / `<подсеть>_EUR.txt`                 | человекочитаемый лог каждого прогона                                     |
| `compare_<подсеть>.txt`                                   | итоговый отчёт сравнения по одной подсети                                |
| `compare_ALL.txt`                                         | сводный отчёт по всем подсетям в папке ("сводный режим")                 |

### Шаг 4. Сводка по всем подсетям ("сводный режим")

Когда в папке накопились прогоны нескольких подсетей одного провайдера, запустите `Compare` **без** `-SubnetBase` — скрипт сам найдёт все пары `result_<подсеть>_EUR.json` + `result_<подсеть>_RUS.json` и сведёт их в общую статистику:

```powershell
.\TSPU_checker.ps1 -Mode Compare
```

Результат — таблица «подсеть / база / заблокировано / процент» по каждой подсети плюс строка «ИТОГО» с общим процентом блокировки по провайдеру. Отчёт сохраняется в `compare_ALL.txt`.

Подсети, у которых есть только один прогон из двух (например, сделан `EUR`, но не сделан `RUS`), в свод не попадают, и перечисляются отдельно как пропущенные. Свод строится только по JSON-файлам результатов; ранее созданные `compare_<подсеть>.txt` при этом не используются.

### Настройка параметров

В начале файла `TSPU_checker.ps1` есть блок `НАСТРОЙКИ`, который можно править вручную под свои задачи:

- **`$Count`** (по умолчанию `20`) — сколько случайных адресов проверять из всей подсети `/24` (всего 255 IP). Больше значение — точнее картина по подсети, но дольше прогон. Для беглой проверки хватает 20..30; для более уверенной статистики можно поднять до 50–100.
- **`$TimeoutMs`** (по умолчанию `400`) — сколько миллисекунд ждать ответа на пинг и на **каждый** порт SSH. Чем меньше, тем быстрее отрабатывают «глухие» адреса, но при слишком малом значении медленный или далёкий сервер может не успеть ответить и будет ошибочно записан как недоступный. 400 мс покрывает подавляющее большинство случаев; при нестабильном канале или очень далёких серверах можно увеличить.
- **`$SSHPorts`** — список портов SSH, которые проверяются по порядку до первого ответившего. По умолчанию перечислены наиболее распространенные 22, 222, 2222.

## 4. Интерпретация результатов

Отчёт `Compare` строится вокруг **базы** — это адреса, на которых SSH ответил **при включенном VPN** (из условной Европы). Такие хосты считаются заведомо живыми и доступными «снаружи»; именно на них имеет смысл смотреть, доступны ли они из России.

Ключевые строки отчёта:

- **`SSH ЗАБЛОКИРОВАНО в RUS: X из Y (Z% от базы)`** — сколько заведомо живых серверов недоступны по TCP из России. Это главный показатель работы ТСПУ. Высокий процент при живом пинге = подсеть режется на уровне протокола TCP.

- **`Пинг был в EUR, нет в RUS`** — на этих адресах из России пропал даже пинг. Значимый признак еще более жёсткой фильтрации подсети.

- **`Пинга не было в EUR, есть в RUS`** — с пометкой **«подозрение на блокировку за спам»**. Ситуация обратная ожидаемой: эталонная точка не видит хост, а российская видит. Единичные значения можно игнорировать (скорее всего разовый отвал по таймауту), а вот большие цифры стоят вашего внимания. Вероятная причина — выходной IP вашего VPN блокируется за частые запросы. Это сигнал, что эталон в этом прогоне не вполне чист. Стоит сделать паузу в тестировании на несколько часов или сменить выходной VPN-узел.

Вердикт по каждому адресу в таблице детализации:

| Вердикт            | Значение                                                               |
| ------------------ | ---------------------------------------------------------------------- |
| `доступен в обеих` | SSH отвечает и из Европы, и из России — блокировки нет                 |
| `SSH заблокирован` | SSH был из Европы, но пропал из России — цель проверки                 |
| `SSH только в RUS` | из России SSH есть, из Европы нет (нетипично, см. пункт про спам)      |
| `SSH недоступен`   | хост отвечает на пинг, но SSH закрыт с обеих сторон (в базу не входит) |
| `нет сервера`      | ни пинга, ни SSH ни с одной стороны — на адресе ничего нет             |

### Как читать итог

**Сценарий А (смена IP у текущего провайдера):**

- Прогоните несколько подсетей одного ASN.
- Если в вашей подсети или у провайдера в целом минимальное число заблокированных адресов, то смело заказывайте смену IP, это скорее всего решит проблему.
- Если ваша подсеть условно заблокирована (высокий процент блокировки), а среди соседних есть чистые (низкий процент блокировки), то смена IP у такого повайдера может быть оправдана. Но стоит принимать такое решение на основе конкретных цифр.
- Если заблокированы (высокий процент блокировки) все проверенные подсети, то смена IP внутри провайдера скорее всего не решит проблему.

**Сценарий Б (выбор нового провайдера):**

- Прогоните несколько разных подсетей ASN провайдера (лучше всего в отдельной папке с имененем провайдера).
- Запустите сводный режим (`-Mode Compare` без подсети). Строка «ИТОГО» даст общий процент блокировки по провайдеру.
- Стабильно низкий процент по всем подсетям — провайдер пригоден.
- Высокий процент в большинстве подсетей — брать VPS у него рискованно, ищите другого.

### Ограничения метода

- Доступность адресов проверяется **непосредственно с вашего компьютера и с вашего выходного VPN**. Соответственно, полученные результаты **валидны только для вашего провайдера**, и могут сильно отличаться в любую сторону, например, при переходе на мобильный интернет. 
- **Проверка пинга и ssh не покрывает весь возможный диапазон блокировок на уровне ТСПУ**. Скрипт не даст вам гарантии, что конкретно у этого провайдера VPS гарантированно заработает. Он лишь дает помогает с предварительной оценкой, избавляя вас от необходимости вычитывать форумы и группы, или тратить деньги на покупку "тестового VPS". Пожалуйста, учитывайте это ограничение.
- Каждый адрес проверяется однократно, без повторов (для сокращения времени проверки). Единичный сетевой сбой возможен, но на качественную картину («режется / не режется подсеть») это обычно не влияет.
- Проверяется случайная выборка адресов `/24`, а не весь диапазон из 255 IP. Для более плотной проверки увеличьте `$Count`.
- Скрипт рассчитан на блок `/24`; более крупные префиксы проверяйте по частям.
- Достоверность эталона зависит от «чистоты» выходного IP VPN.

## Ответственное использование

Скрипт отправляет ICMP-запросы (пинг) и попытки TCP-подключения на порты SSH к чужим IP-адресам. Он не эксплуатирует уязвимости, не передаёт и не собирает никаких данных — только фиксирует факт доступности порта. Тем не менее, массовое сканирование чужих адресов может расцениваться владельцами сетей как нежелательное, и в ряде случаев нарушать условия использования провайдеров. Чем выше интенсивность сканирования, тем больше вероятность появления претензий за "спам". Этот риск вам стоит оценивать самостоятельно.

Инструмент предназначен для диагностики собственной сетевой доступности и оценки целесообразности выбора или смены хостинга. Не используйте его для сканирования сетей, к которым у вас нет законного интереса. Ответственность за применение и соответствие законодательству вашей юрисдикции несёте вы сами.
